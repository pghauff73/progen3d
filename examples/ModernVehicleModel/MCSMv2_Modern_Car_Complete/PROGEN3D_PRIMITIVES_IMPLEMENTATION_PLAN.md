# ProGen3D MCSMv2 Primitive Implementation Plan

**Status:** Implemented and MCSMv2-validated; cross-version release certification retains one inherited `MCP_OMv1` visual exception.

**Date:** 2026-08-24

**Target:** `examples/MVPv2_5_Red_AWD_Hatchback/MCSMv2_Modern_Car_Complete/`
**Primary objective:** Implement the smallest native ProGen3D primitive set that can reproduce the MCSMv2 reference vehicle first, then the complete four-variant family, without breaking MVPv1, MVPv2, MVPv2.5, MVPv2.6, or MCP_OMv1 behavior.

Implementation evidence and the compatibility exception are recorded in
`MCSMv2_NATIVE_IMPLEMENTATION_VERIFICATION.md` and
`tests/evidence/mcsmv2_native_implementation_2026-08-24.json`.

## 1. Fast Delivery Strategy

Use a vertical slice rather than implementing every MCSMv2 concept simultaneously.

The first usable milestone is:

1. Load the reference variant parameters generated by `modern_car_mcsmv2.py`.
2. Evaluate its semantic section field.
3. subtract its four swept wheel envelopes.
4. Generate one watertight native body mesh.
5. Render front, side, and top views.
6. Require deterministic output and silhouette IoU of at least `0.80`.

Only after this slice passes should panel graphs, body-in-white members, occupant envelopes, and functional packages be added.

### Efficiency Rules

- Reuse existing `SurfaceLoft`, `CurveNetworkSurface`, `VariableSectionSweep`, `FormedPanel`, `PanelCut`, `EdgeFlange`, `CompoundShape`, and topology services.
- Extract the existing marching-tetrahedra implementation once; do not create a second MCSMv2-only mesher.
- Keep the Python generator as the source authority until native parity is proven.
- Generate native catalog data; do not manually duplicate the four variant definitions.
- Give every parameter and semantic fact one canonical owner.
- Run low-resolution focused tests during development and full-resolution visual gates only at milestone boundaries.
- Keep the editor preview at bounded LOD and export high-resolution meshes separately.
- Fail closed when source data, coordinate conversion, topology, or evidence is incomplete.

## 2. Scope

### In Scope

- Native MCSMv2 semantic-section model.
- Typed implicit scalar-field graph.
- Swept wheel motion envelopes.
- Generic iso-surface generation.
- Semantic surface and character-curve extraction.
- Panel patch graph.
- Body-in-white assembly graph.
- Occupant and functional package envelopes.
- Executable grammar lowering.
- Deterministic hashes, validation reports, and three-view evidence.
- Four variants: `reference`, `track`, `aero`, and `crossover`.

### Deferred Until the Core Slice Passes

- Production Class-A surfacing.
- Manufacturing-grade panel thickness and hemming.
- Detailed suspension, drivetrain, interior, and closure animation.
- Arbitrary user-authored field expressions in the editor.
- Real-time full-resolution iso-surface regeneration on every editor keystroke.

## 3. Required Object Model

The implementation must remain UML-readable and separate model, relationship, context, and service responsibilities.

### 3.1 Reused Canonical Models

Reuse these existing concepts rather than introducing parallel parameter owners:

- `ModernCarCoordinateFrame`
- `VehiclePackageParameters`
- `VehicleWheelParameters`
- `VehiclePowertrainIntent`
- `ParametricModelGenerationPolicy`
- `GeneratedBodyMesh`
- `MeshTopologyReport`

Add an explicit conversion service when MCSMv2 source values do not exactly match an existing type.

### 3.2 New Model Classes

Place MCSMv2 model classes under `include/vehicle/mcsmv2/model/`.

#### Family and Variant Models

- `ModernCarSemanticFamily` composes the four supported variants.
- `ModernCarSemanticVariant` composes package, platform, style, wheel, powertrain, closure, section, and evidence definitions.
- `ModernCarSemanticSourceManifest` owns generator version, source hashes, coordinate convention, and artifact provenance.
- `ModernCarGenerationContext` associates one variant with generation policy and evidence policy.

#### Semantic Section Models

- `VehicleSemanticSectionField` composes eleven ordered `VehicleSemanticSectionStation` objects.
- `VehicleSemanticSectionStation` composes eight `VehicleSectionLandmark` objects.
- `VehicleSectionLandmark` owns a semantic role and one source-space point.
- `VehicleSemanticStationRole` enumerates tail, axle, door, pillar, hood, nose, and face roles.
- `VehicleSectionLandmarkRole` enumerates underbody, rocker, lower body, shoulder, belt, glass shoulder, roof rail, and roof crown roles.
- `ShapePreservingInterpolationPolicy` owns PCHIP interpolation settings.

#### Character Curve Models

- `VehicleCharacterCurveNetwork` composes fourteen named `VehicleCharacterCurve` objects.
- `VehicleCharacterCurve` owns its semantic role, sampled source points, and section provenance.
- `VehicleCharacterCurveRole` identifies centre spine, roof, glass, belt, shoulder, rocker, and underbody curves.

#### Scalar Field Models

Introduce a real conceptual abstraction:

```text
ImplicitScalarField
  <|-- SemanticSectionBodyField
  <|-- SuperellipsoidField
  <|-- PackageBoundaryField
  <|-- SmoothMaximumField
  <|-- DifferenceField
```

`ImplicitScalarField` declares:

- `evaluateAt(const glm::dvec3 &source_point)`
- `evaluationBounds()`
- `deterministicHash()`

Concrete fields own their inputs explicitly. Do not hide the field graph in anonymous lambdas.

#### Wheel Envelope Models

- `VehicleWheelMotionEnvelope` composes wheel centre, radius, width, steer range, suspension travel, and clearance.
- `VehicleWheelPositionRelationship` associates an envelope with front/rear and left/right axle roles.
- `VehicleWheelEnvelopeSet` composes exactly four wheel envelopes.

#### Surface, Panel, and Engineering Models

- `VehicleSemanticSurface` owns the generated semantic surface and section/curve provenance.
- `VehiclePanelPatchGraph` composes `VehiclePanelPatch` and `VehiclePanelAdjacencyRelationship` objects.
- `VehicleBodyInWhiteAssembly` composes purpose-specific structural members.
- `BodyInWhiteJointRelationship` associates two structural members through a shared datum.
- `VehicleOccupantEnvelopeSystem` composes seat, eye-point, head-clearance, and reach envelopes.
- `VehicleFunctionalPackageSystem` composes powertrain and storage envelopes.

## 5. Implementation Phases

Indicative delivery targets assume one focused developer using the existing ProGen3D geometry stack:

| Milestone | Target effort | Cumulative result |
|---|---:|---|
| Source contract | `0.5 day` | deterministic native inputs |
| Generic iso-surface kernel | `1 day` | reusable field meshing |
| Reference vertical slice | `1.5 days` | first accepted native MCSMv2 vehicle |
| Four-variant family | `1 day` | parametric family body generation |
| Semantic curves and surface | `1 day` | semantic design structure |
| Engineering object graphs | `1.5-2 days` | panels, body-in-white, occupants, packages |
| Grammar and release audit | `1 day` | executable examples and compatibility evidence |

The first visible accepted vehicle should therefore be targeted within approximately three focused development days. These are planning estimates, not completion evidence.

### Phase 0 - Freeze the Source Contract

**Goal:** Establish an exact baseline before native implementation.

Tasks:

1. Add a generator mode that emits a deterministic MCSMv2 native catalog artifact.
2. Record source hashes for the Python generator, variant data, station data, curve data, and target grammar.
3. Document the coordinate mapping:
   - MCSMv2 source: `+X` longitudinal/front, `+Y` lateral/right, `+Z` up.
   - ProGen3D: `+X` right, `+Y` up, `+Z` forward.
   - Conversion: `progen(x,y,z) = source(y,z,x)`.
4. Remove committed `__pycache__` directories and `.pyc` files.
5. Add a two-run generator determinism check.

Exit gate:

- Two generator runs produce identical hashes and artifact lists.
- All four variants have finite, complete, and ordered source data.

### Phase 1 - Extract the Generic Iso-Surface Kernel

**Goal:** Reuse one meshing implementation for MCP_OMv1 and MCSMv2.

Tasks:

1. Introduce `ImplicitScalarField`.
2. Introduce `ImplicitSurfaceGenerationRequest` with bounds, iso value, sample counts, smoothing, normalization, and LOD.
3. Move marching-tetrahedra assembly from `ModernCarIsoSurfaceGenerationService` into `ImplicitSurfaceMeshingService`.
4. Adapt `ModernCarIsoSurfaceGenerationService` to the generic service without changing output hashes unless a documented defect requires correction.
5. Add field-independent sphere and box iso-surface tests.

Exit gate:

- MCP_OMv1 native generation tests still pass.
- Generic sphere and box fields generate finite, watertight meshes.
- Identical requests produce identical mesh hashes.

### Phase 2 - Build the Reference Vertical Slice

**Goal:** Produce the first native MCSMv2 body as quickly as possible.

Tasks:

1. Generate the reference variant catalog entry.
2. Implement semantic station and landmark models.
3. Implement PCHIP section interpolation.
4. Implement `SemanticSectionBodyField`.
5. Implement four `VehicleWheelMotionEnvelope` objects.
6. Compose the body using `DifferenceField`.
7. Generate the reference body at low development resolution.
8. Convert the mesh into ProGen3D coordinates.
9. Render front, side, and top evidence views.

Exit gate:

- Body is finite, watertight, manifold, grounded, and correctly oriented.
- Wheel-envelope clearance passes.
- Front, side, and top silhouette IoU are each at least `0.80`.
- A second run produces the same mesh and evidence hashes.

This phase is the first releaseable development milestone.

### Phase 3 - Expand to the Four-Variant Family

**Goal:** Prove that the model is parametric rather than reference-specific.

Tasks:

1. Generate `track`, `aero`, and `crossover` catalog entries.
2. Reuse the same field graph and services for every variant.
3. Add variant-specific package-bound correction only through typed parameters.
4. Generate low, preview, and evidence LOD policies.
5. Compare native section samples and field samples against the Python reference.

Exit gate:

- All four variants pass topology, bounds, grounding, orientation, wheel-clearance, and deterministic-hash checks.
- All twelve front/side/top comparisons meet `IoU >= 0.80`.
- No variant-specific procedural branch is added unless represented as an explicit style policy.

### Phase 4 - Add Semantic Curves and Surface

**Goal:** Preserve semantic design structure, not only the final implicit mesh.

Tasks:

1. Extract the fourteen character curves from the section field.
2. Validate curve-to-section intersections within `0.002 m`.
3. Generate `VehicleSemanticSurface` with existing surface-loft infrastructure.
4. Preserve station, landmark, and curve provenance on generated mesh tags.
5. Compare surface samples with Python outputs.

Exit gate:

- Curves are ordered, finite, and intersect their source sections.
- Surface normals and topology are valid.
- Semantic surface hashes are deterministic.

### Phase 5 - Add Panels and Engineering Objects

**Goal:** Complete the MCSMv2 semantic and engineering graph.

Tasks:

1. Implement panel patch selection using semantic tags before geometric cutting.
2. Create hood, roof, doors, quarters, hatch, and bumper patches.
3. Add adjacency relationships and panel validation.
4. Build body-in-white members with `VariableSectionSweep`, `FormedPanel`, and `CompoundShape`.
5. Add explicit body-in-white joint relationships.
6. Add occupant and functional package envelopes.

Exit gate:

- Required panels exist and have valid adjacency.
- Body-in-white graph is connected.
- Occupant envelopes remain contained.
- Functional envelopes fit inside the package without invalid intersections.

### Phase 6 - Make the Grammar Executable

**Goal:** Replace the descriptive target grammar with parser-supported, lowered geometry.

Tasks:

1. Add grammar symbols only after their model and service owners exist.
2. Parse `SemanticSectionField`, `CharacterCurveNetwork`, `ImplicitScaffold`, `SweptWheelEnvelope`, `IsoSurface`, and validation declarations.
3. Add `GeneratedMeshReference` as a compact grammar primitive that resolves an immutable `ProceduralMeshRepository` key.
4. Lower compact semantic declarations into `GeneratedMeshReference` instances rather than embedding mesh vertices in grammar text.
5. Require a material argument for every geometric `!I(...)` instance.
6. Keep validation declarations outside geometry instance syntax.
7. Generate one executable grammar per variant plus a family catalog grammar.

Target semantic grammar:

```text
MCSMv2ReferenceBody ->
[
    !I(
        IsoSurface(
            field(
                DifferenceField(
                    source(SemanticSectionBodyField(MCSMv2ReferenceSections))
                    subtract(MCSMv2ReferenceWheelEnvelopes)
                )
            )
            isoValue(0)
            resolution(128 72 72)
            detail(LOD2)
        )
        material(redmetallicpaint)
        alpha(1)
        texscale(0.16)
    )
]
```

Fast executable lowering:

```text
MCSMv2ReferenceBody ->
[
    !I(
        GeneratedMeshReference(
            meshKey(MCSMv2ReferenceBodyMesh)
            detail(LOD2)
        )
        material(redmetallicpaint)
        alpha(1)
        texscale(0.16)
    )
]
```

Exit gate:

- All generated grammars parse without fallback entry rules.
- No `Instance syntax requires a material argument` diagnostic occurs.
- Grammar-generated meshes match direct-service hashes.

## 6. Fast Development Test Matrix

| Development loop | Resolution | Variants | Required checks |
|---|---:|---|---|
| Field math | sampled points only | reference | finite values, Python parity |
| Mesh smoke | `32 x 20 x 20` | reference | non-empty, finite, bounded |
| Topology loop | `64 x 36 x 36` | reference | watertight, manifold, clearance |
| Family loop | `64 x 36 x 36` | all four | deterministic hashes, package bounds |
| Visual preview | LOD2 | all four | front/side/top orientation and grounding |

Do not run full-resolution exports during ordinary unit-test iteration.

## 7. Performance and Editor Safety

- Cache field samples by variant hash and generation policy hash.
- Cache generated meshes in `ProceduralMeshRepository`.
- Separate preview LOD from evidence and export LOD.
- Use bounded editor preview meshes below the 16-bit draw-index limit per draw list.
- Split large meshes into deterministic submeshes when necessary.
- Do not inline tens of thousands of vertices into grammar text.
- Perform expensive generation outside the render loop.
- Preserve the last valid scene when parsing or generation fails.

## 9. Completion Definition

The implementation is complete only when:

1. The target MCSMv2 grammar concepts have explicit native model or relationship owners.
2. All four variants are generated through the same parametric architecture.
3. Native field and section samples agree with the Python reference within documented tolerances.
4. Bodies are finite, grounded, correctly oriented, watertight, manifold, and deterministic.
5. Wheel, occupant, package, panel, and body-in-white validations pass.
6. Front, side, and top silhouette IoU is at least `0.80` for every variant.
7. Direct-service and grammar-generated output hashes agree.
8. MCP_OMv1 and MVPv1 through MVPv2.6 compatibility gates pass.
9. Documentation records source hashes, generated hashes, limitations, and evidence paths.

## 10. Fastest Critical Path

The shortest safe path is:

```text
Source Contract
    -> Generic Implicit Mesher
    -> Reference Semantic Sections
    -> Reference Wheel Envelopes
    -> Reference Body Mesh
    -> Three-View Gate
    -> Four Variants
    -> Grammar Lowering
    -> Engineering Graphs
    -> Compatibility Audit
```

This ordering produces visible, testable geometry early while postponing non-blocking engineering detail. It also creates one reusable implicit-geometry foundation rather than adding another isolated vehicle generator.
