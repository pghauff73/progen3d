ProGen3D MVPv2 Hatchback Fitting Implementation Plan

Reading guide: this source section records “ProGen3D MVPv2 Hatchback Fitting Implementation Plan”. Distinguish stated behavior from proposed or pending work using the status styling.

1. Objective

Reading guide: this source section records “1. Objective”. Distinguish stated behavior from proposed or pending work using the status styling.

Promote the red AWD hatchback from an MVPv1 section-loft plus decorative panel-cut model to an MVPv2 spatial fitting model whose body and closures are described by evidence-bearing semantic objects.

The authoritative construction sequence is:

Reference views
→ multi-view envelope
→ semantic cross-sections and surface landmarks
→ character-curve network
→ projection-constrained boundary patches
→ panel seam loops and extracted panels
→ apertures and closure assemblies
→ kinematic relationships
→ validated vehicle state and deterministic evidence

MVPv2 shall coexist with MVPv1. Existing VehicleBodyShell, VehicleJoint, examples, exports, and renderer paths remain legal while the richer object model is introduced.

2. Current Architectural Baseline

Reading guide: this source section records “2. Current Architectural Baseline”. Distinguish stated behavior from proposed or pending work using the status styling.

The current vehicle model provides:

  • package, intent, datum, style, wheel, suspension, body, interior, exterior, and powertrain specifications;
  • VehicleBodySection, represented as an arbitrary right-half profile at an axial station;
  • VehicleSurfaceGuide, WheelArchSpecification, and VehiclePanelCutSpecification;
  • one body-wide shell loft generated by VehicleBodyAssemblyBuilder;
  • fixed, revolute, prismatic, and ball VehicleJoint declarations;
  • deterministic assembly hashing and topology validation;
  • grammar examples that lower semantic vehicle descriptions to existing FGKv1 geometry.

The missing responsibilities are:

  • no semantic cross-section landmarks;
  • no per-view observation/evidence model;
  • no character-curve relationship graph;
  • no patch boundary or patch continuity graph;
  • no panel extraction or aperture model;
  • no complete door, bonnet, hatch, or moving-glass assembly;
  • no hinge-point pair, guide-rail, four-bar, or telescoping-link relationship;
  • no closure dependency graph or swept-volume evidence;
  • no deterministic hash over fitting and closure semantics.

3. P0 Promotion Boundary

Reading guide: this source section records “3. P0 Promotion Boundary”. Distinguish stated behavior from proposed or pending work using the status styling.

P0 implements the full semantic and kinematic object model without attempting a production automotive Class-A surface optimizer.

P0 includes:

  1. deterministic multi-view silhouette samples and weights;
  2. semantic vehicle cross-sections;
  3. observed surface landmarks;
  4. named character curves and curve relationships;
  5. boundary patches and projection constraints;
  6. surface-patch edge continuity relationships;
  7. seam loops and extracted panel records;
  8. apertures with flange, seal, reinforcement, and mounting features;
  9. complete side-door, bonnet, hatch, and drop-glass assemblies;
  10. hinge pairs, four-bar joints, guide-rail joints, and telescoping links;
  11. normalized closure state values;
  12. deterministic transforms and sampled swept AABBs;
  13. dependency validation, including door-local glass motion;
  14. semantic validation and deterministic evidence hashing;
  15. a researched red AWD hatchback acceptance fixture;
  16. a grammar-facing example lowered to existing renderable primitives.

P0 deliberately excludes:

  • nonlinear projection optimization of mesh control points;
  • exact NURBS/Class-A patch evaluation;
  • UV-domain Boolean panel extraction;
  • exact collision meshes for moving closures;
  • inferred hidden mechanism certification;
  • production-grade four-bar synthesis;
  • automatic landmark detection from images.

These exclusions are explicit rather than silently approximated.

5.2 Hinge pair

Reading guide: this source section records “5.2 Hinge pair”. Distinguish stated behavior from proposed or pending work using the status styling.

HingePair stores upper and lower body-mount points. Its normalized axis is derived from those points. A zero-length pair is invalid.

Side-door transform:

T(q) = Translate(pivot)
       Rotate(axis, q * maximumAngle)
       Translate(-pivot)

5.3 Four-bar joint

Reading guide: this source section records “5.3 Four-bar joint”. Distinguish stated behavior from proposed or pending work using the status styling.

FourBarJoint stores two body mounts and two closure mounts. P0 derives a deterministic approximate panel transform from the interpolated hinge axis plus the average mount displacement. This is explicitly classified as an inferred engineering model.

5.4 Guide-rail joint

Reading guide: this source section records “5.4 Guide-rail joint”. Distinguish stated behavior from proposed or pending work using the status styling.

GuideRailJoint stores front and rear rail curves plus front and rear glass follower points. Evaluating both rails at the same normalized state determines translation and orientation.

The world glass transform is:

T_world_glass = T_world_door * T_door_glass(q)

This dependency is mandatory and validated.

5.5 Telescoping link

Reading guide: this source section records “5.5 Telescoping link”. Distinguish stated behavior from proposed or pending work using the status styling.

TelescopingLink stores body mount, closure mount, minimum length, and maximum length. It validates bonnet supports and hatch gas struts across the closure state range.

5.6 Swept volume

Reading guide: this source section records “5.6 Swept volume”. Distinguish stated behavior from proposed or pending work using the status styling.

P0 SweptVolume stores a deterministic union AABB sampled over a fixed ordered state sequence. The record includes sample count, minimum state, maximum state, local source bounds, and resolved swept bounds.

This is broad-phase evidence, not an exact swept solid.

7. Validation Contract

Reading guide: this source section records “7. Validation Contract”. Distinguish stated behavior from proposed or pending work using the status styling.

VehicleFittingValidationService fails closed for:

  • duplicate or empty identifiers;
  • missing required front/side/top evidence;
  • non-finite points, weights, tolerances, or state;
  • out-of-range normalized coordinates and closure states;
  • unordered cross-section stations;
  • missing required cross-section landmark roles;
  • invalid or missing curve references;
  • invalid patch boundary count;
  • missing patch references in continuity relationships;
  • open seam loops;
  • aperture boundaries that do not match panel seams;
  • invalid hinge pairs;
  • invalid four-bar mount geometry;
  • invalid guide rails or coincident glass followers;
  • invalid telescoping-link ranges;
  • closure dependencies that reference missing parents;
  • dependency cycles;
  • moving glass that is not parented to its owning door;
  • swept volume with non-finite or inverted bounds;
  • inferred hidden hardware incorrectly marked as observed.

Diagnostics receive stable MVPv2 codes in VehicleValidationReport.

8. Determinism Contract

Reading guide: this source section records “8. Determinism Contract”. Distinguish stated behavior from proposed or pending work using the status styling.

The same evaluated fitting architecture must produce identical:

  • semantic object ordering;
  • curve ordering;
  • patch ordering;
  • closure ordering;
  • kinematic transform samples;
  • swept bounds;
  • validation report;
  • deterministic hash.

VehicleFittingDeterministicHashService hashes evaluated values and semantic relationships. It never hashes object addresses, expression text, unordered containers, or locale-formatted strings.

The existing assembly hash remains available. MVPv2 adds a combined semantic evidence hash.

9. Grammar and Editor Integration

Reading guide: this source section records “9. Grammar and Editor Integration”. Distinguish stated behavior from proposed or pending work using the status styling.

P0 keeps renderable geometry on existing FGKv1 shapes and adds a documented lowering pattern:

MVPv2 semantic object
→ existing Object / Interface / Joint declarations
→ SurfaceLoft, ShellLoft, CurvedPanel, PanelCut, SweepDisk, and primitives

The grammar-facing acceptance example shall:

  • use named body, door, bonnet, hatch, glass, hinge, latch, seal, and guide-rail objects;
  • declare two-point hinge evidence as interfaces;
  • preserve four moving door relationships;
  • preserve bonnet and hatch relationships;
  • express glass as door-contained objects;
  • use current renderable geometry while documenting inferred hidden mechanisms;
  • remain parseable by the current editor and supervisor mode.

The editor inspector can initially report MVPv2 data through generated evidence output. Native interactive patch/closure editors are post-P0.
