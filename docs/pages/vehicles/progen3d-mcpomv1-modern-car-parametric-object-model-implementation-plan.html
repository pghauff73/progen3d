ProGen3D MCP_OMv1 Modern Car Parametric Object Model Implementation Plan

Reading guide: this source section records “ProGen3D MCP_OMv1 Modern Car Parametric Object Model Implementation Plan”. Distinguish stated behavior from proposed or pending work using the status styling.

1. Objective

Reading guide: this source section records “1. Objective”. Distinguish stated behavior from proposed or pending work using the status styling.

Create MCP_OMv1, the Modern Car Parametric Object Model v1, by converting the research and generator logic in:

examples/MVPv2_5_Red_AWD_Hatchback/Modern_Car_MCSMv1/

into a typed, deterministic, provenance-bearing ProGen3D object model.

MCP_OMv1 owns the parametric family definition and generated candidate realizations. It does not replace the evidence-constrained automotive authority already implemented by MVPv2.5. MVP2.6 composes both models:

MVP2.6
  = preserved MVPv2.5 semantic authority
  + MCP_OMv1 parametric family source
  + explicit source-to-authority fitting evidence

The implementation must retain all MVPv1, MVPv2, and MVPv2.5 compatibility gates.

2. Current Baseline

Reading guide: this source section records “2. Current Baseline”. Distinguish stated behavior from proposed or pending work using the status styling.

The MCSMv1 package currently provides:

  • four vehicle variants: reference, track, aero, and crossover;
  • package, wheel, style, and powertrain parameters;
  • a Python implicit-field and marching-cubes generator;
  • generated GLB, OBJ, and watertight body STL artifacts;
  • reference-variant character curves and body sections;
  • orthographic and isometric previews;
  • validation and checksum records;
  • a proposed grammar that is explicitly not compatible with the current ProGen3D parser.

The existing MVPv2.5 implementation already owns:

  • calibrated reference observations;
  • the authoritative vehicle package and reference frame;
  • semantic landmarks, wireframe, and silhouette constraints;
  • Class-A surface patches and highlight-flow validation;
  • panel gaps, apertures, closures, glass motion, and seals;
  • BIW, suspension, wheels, tyres, rims, brakes, and wheel houses;
  • aero geometry, fitting residuals, and deterministic hashes.

MCP_OMv1 must therefore be additive. Generated MCSMv1 meshes are candidate geometry, not a replacement for the MVPv2.5 semantic graph.

3.1 Current executable grammar

Reading guide: this source section records “3.1 Current executable grammar”. Distinguish stated behavior from proposed or pending work using the status styling.

The current parser can execute:

  • parameterized production rules;
  • Object, Interface, Position, and Joint records;
  • transforms such as T, S, and A;
  • procedural shapes including VehicleBodyShell, SurfaceLoft, ShellOffset, SweepDisk, Revolve, Extrude, and CompoundShape;
  • explicit instance material, alpha, and texture-scale arguments.

The current parser cannot execute MCSMv1 terms such as ImplicitSectionField, IsoSurface, StationInterpolation, or GenerateCandidateRealization.

Every .p3d file added during MCP_OMv1 P0-P5 must therefore use the current parser. Future semantic syntax belongs in documentation until the corresponding model, parser, evaluator, and geometry services exist.

4. Coordinate Model

Reading guide: this source section records “4. Coordinate Model”. Distinguish stated behavior from proposed or pending work using the status styling.

MCSMv1 uses:

+x = vehicle front
+y = vehicle right
+z = vehicle up

MVP and ProGen3D vehicle models use:

+X = vehicle right
+Y = vehicle up
+Z = vehicle forward

The authoritative conversion is:

MVP.X = MCSM.y
MVP.Y = MCSM.z
MVP.Z = MCSM.x

ModernCarCoordinateFrame owns this relationship. Geometry services consume the conversion; they must not copy or rediscover it.

The MCP_OMv1 local origin is the ground projection of the vehicle package centre. Axle locations are therefore:

front axle = (0, wheel radius, +wheelbase / 2)
rear axle  = (0, wheel radius, -wheelbase / 2)

7. Generator and Provenance Strategy

Reading guide: this source section records “7. Generator and Provenance Strategy”. Distinguish stated behavior from proposed or pending work using the status styling.

The existing Python generator remains the first source implementation. Do not copy its variant constants into handwritten C++.

Refactor it into importable responsibilities:

McsM1VariantCatalog
McsM1FieldDefinitionFactory
McsM1VehicleGenerator
McsM1ArtifactWriter
McsM1ValidationReporter

Add tools/generate_mcp_omv1_artifacts.py as the canonical bridge. It imports the refactored MCSMv1 module and writes:

  • normalized MCP_OMv1_FamilyDefinition.json;
  • normalized MCP_OMv1_SourceManifest.json;
  • generated C++ catalog records used by ModernCarParametricCatalogFactory;
  • per-variant curve, section, camera, and validation artifacts;
  • current-parser .p3d preview lowerings;

The generated C++ records must embed the source JSON hash and must never be edited manually. This avoids a runtime JSON dependency while retaining the MCSMv1 source as the canonical owner.

Remove __pycache__ and .pyc files from the canonical package and checksum manifest. Record exact generator dependency versions in a lock file. Exclude timestamps, temporary directories, and machine-specific paths from deterministic hashes.

16. Completion Standard

Reading guide: this source section records “16. Completion Standard”. Distinguish stated behavior from proposed or pending work using the status styling.

MCP_OMv1 is complete only when:

  • MCSMv1 is refactored and remains the generator source rather than being duplicated;
  • four typed variants exist with one canonical owner for every parameter;
  • coordinate conversion and package-centre placement are explicit;
  • all variants generate deterministic body, curve, section, and view evidence;
  • current-parser family and adapter grammars execute without diagnostics;
  • every variant exceeds 0.80 silhouette IoU in front, side, and top views;
  • the reference variant integrates into MVP2.6 without weakening any accepted MVPv2.5 validation;
  • MVPv1, MVPv2, MVPv2.5, MCP_OMv1, and MVP2.6 gates pass;
  • provenance, limitations, hashes, and evidence remain reviewable.
